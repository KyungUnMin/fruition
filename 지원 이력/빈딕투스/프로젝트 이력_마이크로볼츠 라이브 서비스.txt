[ 대량 로그 처리 누락 개선]
 일 평균 약 12만 건의 로그가 누락되던 문제를 분석하고 처리 구조를 개선하여, 이후 1년이 지난 현재까지 로그 누락 재발 없이 안정적인 운영을 유지했습니다.
 사업팀이 운영툴을 통해 로그를 조회할 때 다수의 로그가 누락되어 CS 대응이 지연되고, 서버팀에 로그 분석 요청이 반복되는 병목이 발생했습니다. 이를 단순한 로그 오류가 아니라 CS 대응과 서버팀의 분석 업무까지 영향을 주는 프로세스상의 문제로 판단하고 원인 분석에 착수했습니다. 분석 결과, MySQL 이벤트로 주기적으로 실행되는 파티셔닝 프로시저에서 Bulk Insert가 실패할 경우 해당 배치의 로그가 정상적으로 파티셔닝되지 않고 오류 로그 보관 테이블에만 기록되는 구조임을 확인했습니다. 이로 인해 데이터 자체는 존재하지만 운영툴에서는 해당 로그를 조회할 수 없어, 로그가 누락된 것처럼 보이는 문제가 발생했습니다.
 문제 해결을 위해 INSERT IGNORE 방식(소량 누락 감수, 성능 유지)과 Error Handler 방식(단건 재삽입, 성능 저하)을 비교했습니다. 로그가 게임 운영의 근거 데이터라는 점을 고려하여 데이터 누락을 방지할 수 있는 Error Handler 방식을 선택했습니다. 이후 Bulk Insert 실패 시 실패 데이터를 단건으로 재삽입하도록 처리 구조를 개선했습니다.
 개선 이후 현재까지 1년간 동일 유형의 로그 누락이 재발하지 않았으며, 운영툴의 로그 조회 누락으로 인한 CS 대응 지연과 서버팀의 반복적인 로그 분석 요청을 해소할 수 있었습니다.

[기획 데이터 기반 출석판 시스템 설계]
 출석판의 동작 방식을 기획 데이터로 정의하는 구조를 도입하여, 신규 출석판 추가 시 서버 코드 수정 범위를 최소화했습니다.
 기존에는 주간/월간 출석판처럼 출석판 타입별로 로직이 분리되어 있어, 새로운 출석판을 추가할 때마다 서버 코드와 DB를 함께 수정해야 했습니다. 이를 개선하기 위해 출석 시작 기준(항상 1일차 시작 / 이벤트 경과일 기준)과 결석 처리 방식(허용 / 미허용)을 기획 데이터의 플래그로 분리하여, 신규 출석판의 동작을 플래그 조합으로 정의할 수 있도록 구조화했습니다. 다만 각 출석판의 고유 동작을 처리하는 모듈은 서버 코드로 구현해야 했으며, 당시에는 enum으로 모듈을 구분했습니다. 이후 타 프로젝트에서 기획 데이터에 JSON 형태로 모듈과 인자를 함께 정의하는 구조를 접하면서, 모듈별 가변 인자가 필요한 경우에도 데이터만으로 확장할 수 있다는 점을 확인했습니다. 이를 통해 향후에는 모듈과 인자를 데이터로 함께 정의하는 방식이 보다 확장성 있는 구조가 될 수 있음을 배웠습니다.
 유저 출석 데이터 저장 방식도 장단점을 비교하여 설계했습니다. 출석 이벤트마다 개별 레코드를 INSERT하는 방식과 유저 ID 및 출석판 타입 단위로 하나의 레코드를 유지하면서 출석 상태를 BIGINT 비트 플래그로 표현하는 방식을 비교했습니다. 레코드 수를 줄이고 조회 및 INSERT에 대한 부담을 낮출 수 있다는 점을 고려하여 후자를 선택했으며, 비트 플래그의 낮은 가독성을 보완하기 위해 값을 확인할 수 있는 조회용 프로시저를 함께 제공했습니다.
 다만 BIGINT의 특성상 최대 64일까지 출석 상태를 표현할 수 있다는 한계가 있었습니다. 다시 설계한다면 BIGINT 대신 문자열 형태로 출석 상태를 저장하여, 고정된 64비트 제한 없이 64일을 초과하는 출석 기간에도 대응할 수 있도록 개선할 것입니다.

[무기 튜닝 시스템 구조 개선]
 튜닝 데이터를 재활용 가능한 공통 자산으로 분리하여, 유사 무기 추가 시 설계·검증 비용을 구조적으로 줄였습니다.
 기존에는 무기 테이블에 무기 성능 컬럼과 튜닝 데이터가 함께 포함되어 있었으며, 무기는 총 4가지 방식으로 튜닝할 수 있는 구조였습니다. 이로 인해 신규 무기 1개를 추가할 때마다 튜닝 방식별로 최대 4개의 데이터를 반복 생성해야 했고, 유사한 무기를 설계할수록 중복 데이터와 검증 비용이 증가하는 문제가 있었습니다. 무기 자체의 정보와 튜닝 데이터가 하나의 테이블에 강하게 결합된 구조라 판단하여, 무기 테이블과 튜닝 테이블을 분리하는 방향으로 개선했습니다.
 별도 튜닝 테이블을 신규 설계하고 무기를 그룹화하여, 하나의 튜닝 데이터를 여러 무기에서 재사용할 수 있는 구조로 전환했습니다. 이를 통해 기존에 검증된 튜닝 데이터를 재활용해 신규 무기를 설계할 수 있게 되었으며, 신규 무기 추가 시 반복적인 튜닝 데이터 생성과 검증 작업을 줄일 수 있었습니다. 또한 튜닝 데이터가 개별 무기에 종속된 데이터가 아닌 여러 무기에서 활용할 수 있는 공통 자산으로 관리되도록 구조를 개선했습니다.
