    - 출석판 정의 테이블
        
        ```sql
        CREATE TABLE `AttendanceBoardInfo` 
        (
        	`ab_board_id` INT UNSIGNED NOT NULL COMMENT '출석판 ID',
        	`ab_start_time` INT UNSIGNED NOT NULL COMMENT '이벤트 시작일(Unix Timestamp, 초 단위)',
        	`ab_end_time` INT UNSIGNED NOT NULL COMMENT '이벤트 종료일(Unix Timestamp, 초 단위)',
        	`ab_target_type` ENUM('ALL','NEW','RETURN') NOT NULL DEFAULT 'ALL' COMMENT '출석판 대상 유형 (ALL: 전체유저, NEW: 신규유저, RETURN: 복귀유저)' COLLATE 'utf8mb4_unicode_ci',
        	`ab_total_days` INT UNSIGNED NOT NULL COMMENT '총 출석 일수 (예: 7일, 14일, 30일. 최대 64일)',
        	`ab_start_mode` ENUM('FIXED','RELATIVE') NOT NULL COMMENT '출석 시작 기준 방식 (FIXED: 항상 1일차부터 시작, RELATIVE: 이벤트 시작일부터 경과 일수에 맞춰 시작. 예: 이벤트 3일차에 참여하면 3일차부터 시작)' COLLATE 'utf8mb4_unicode_ci',
        	`ab_skip_absent` ENUM('FALSE','TRUE') NOT NULL COMMENT '결석 처리 방식 (FALSE: 결석 시 해당 일차 건너띔, TRUE: 결석일 무시하고 다음 출석으로 이어감)' COLLATE 'utf8mb4_unicode_ci',
        	`ab_desc` VARCHAR(100) NOT NULL COMMENT '출석판 이름 혹은 설명 (예: 신규 유저 7일 출석)' COLLATE 'utf8mb4_unicode_ci',
        	PRIMARY KEY (`ab_board_id`) USING BTREE
        )
        COMMENT='출석판을 정의하는 테이블';
        ```
        
        테이블 사용 예시
        
        | ab_board_id | ab_start_time | ab_end_time | ab_target_type | ab_total_days | ab_start_mode | ab_skip_absent | ab_desc |
        | --- | --- | --- | --- | --- | --- | --- | --- |
        | 0 | 1762858800 | 2551777200 | NEW | 16 | FIXED | FALSE | new attendance edition |
        | 1 | 1762858800 | 2551777200 | RETURN | 16 | FIXED | FALSE | return attendance board |

    - 출석판 조건 테이블
        
        ```sql
        CREATE TABLE `AttendanceConditionInfo` 
        (
        	`ac_board_id` INT UNSIGNED NOT NULL COMMENT '출석판 ID (AttendanceBoardInfo 참조)',
        	`ac_condition` ENUM('LEVEL','PLAYTIME') NOT NULL COMMENT '조건 타입.' COLLATE 'utf8mb4_unicode_ci',
        	`ac_min_value` INT NULL DEFAULT '-2147483648' COMMENT '조건 최솟값',
        	`ac_max_value` INT NULL DEFAULT '2147483647' COMMENT '조건 최댓값',
        	PRIMARY KEY (`ac_board_id`, `ac_condition`) USING BTREE
        )
        COMMENT='출석판 활성 조건을 정의하는 테이블';
        ```
        
         `ac_condition` 컬럼의 enum값으로 출석 조건 판단
        
        AttendanceBoardInfo(출석판 정의) 테이블과  AttendanceConditionInfo(출석판 조건) 테이블은 1:N관계로 출석판 1개에 대해서 여러개의 조건을 설정해줄 수 있음

        CREATE TABLE `player_attendance`

        테이블 사용 예시
        
        | pa_aid | pa_board_id | pa_first_time | pa_last_time | pa_attendance_state |
        | --- | --- | --- | --- | --- |
        | 1 | 1 | 1787583727 | 1787583727 | 1 |
        | 1 | 200 | 1763373033 | 1764232133 | 1543 |
        | 1 | 303 | 1763545833 | 1763545833 | 1 |
        | 1 | 304 | 1763545833 | 1763545833 | 1 |
        
        요구사항처럼 결석 시 건너뛰는 경우가 존재하기 때문에,
        출석 상태 관리를 **출석 데이터 누적 방식**과 **비트 플래그 방식**을 비교 검토.

        **향후 문자열 기반 방식으로의 개선 가능성을 인지**함

    ### 아쉬운 점 / 개선 인식
    
    </aside>
    
    다른 프로젝트 및 타 게임 사례를 통해,
    **출석 조건을 JSON(XML) 형태로 정의**하고 이를 파싱하여
    **조건 모듈 객체**를 바탕으로 출석 여부를 판정하는 구조를 확인함.
    
    - 다른 프로젝트에서 사용되었던 방식 예시
        
        
        | Index | Name | BeginTime | EndTime | SegmentTargeting |
        | --- | --- | --- | --- | --- |
        | 998 | 200430GoldenWeek | 2020-04-29 15:00:00 | 2029-05-06 14:59:59 | JSON 형식으로
        조건 모듈 기록 |
        
        ```json
        [	
        	{
        		"SegmentId":"clear_dungeon",
        		"Options":
        		[
        			{"chapter_index":1,"dungeon_index":1},
        			{"chapter_index":1,"dungeon_index":2},
        			{"chapter_index":1,"dungeon_index":3},
        			{"chapter_index":3,"dungeon_index":1}
        		]
        	},
        	
        	{
        		"SegmentId":"user_targeting",
        		"Options":
        		{
        			"operator":"OR",
        			"items":
        			[
        				{"SegmentId":"newbie"},
        				{"SegmentId":"attendance_return"},
        				{"SegmentId":"current_user","Options":{"return_days":7}}
        			]
        		}
        	}
        ]
        ```
        
    
    이번 프로젝트에서는 출석 조건을 테이블 기반으로 관리했으나,
    JSON/XML 기반 구조를 활용했다면 조건 표현의 자유도와 확장성이 더 높았을 것이라고 판단함.
    (또한 기획자 입장에서는 기능이 여러 테이블로 분리되어 있는 것을 원하지 않기 때문)
    
    차후 유사 시스템 구현 시에는
    출석 조건을 구조화된 데이터(JSON/XML)로 정의하고,
    이를 기반으로 조건 모듈을 구성하는 방식으로 개선할 계획임.

- 3C4P
    
    ### Customer (고객 / 상황)
    
    - 신규·복귀 유저 출석 이벤트마다 **출석 시작 기준, 누적 방식, 결석 처리 규칙이 상이**했으며
    - 이벤트 추가 시마다 서버 로직을 개별 수정해야 해 **운영 및 개발 비용이 지속적으로 증가**하는 상황
    
    ---
    
    ### Company (자사 / 나)
    
    - 서버 프로그래머로서 **이벤트 단위 구현이 아닌 시스템 단위 설계**가 필요하다고 판단
    - 기획 데이터 기반으로 로직을 제어하는 구조를 통해 **확장성과 유지보수성을 개선**
    
    ---
    
    ### Competitor (경쟁 환경 / 대안)
    
    - 출석 이벤트를 개별 구현하는 방식은 초기 개발은 빠르지만
        
        이벤트 유형 증가 시 **복잡도와 유지보수 비용이 급격히 증가**하는 한계가 있었음
        
    - 이에 비해 **출석 조건을 데이터로 분리한 구조가 장기적으로 경쟁력 있는 방식**이라고 판단
    
    ---
    
    ## 4P 분석 (What & How)
    
    ### Product (결과물)
    
    - 출석 이벤트 로직을 **범용 출석판 시스템**으로 분리하고
    - 출석 시작 기준, 누적 방식, 결석 처리 여부 등을 **기획 데이터로 제어 가능한 구조**로 구현
    - 출석 이벤트뿐 아니라 **시즌 패스 등 유사 보상 시스템으로 확장 가능한 기반 확보**
    
    ---
    
    ### Price (문제 해결 / 비용)
    
    - 다양한 출석 규칙을 하나의 시스템에서 처리하기 위해
        
        **출석 조건 관리 테이블 설계 및 상태 관리 로직 복잡도 증가**
        
    - 출석 누적 상태를 비트 플래그로 관리하며 **성능·저장 효율과 구현 난이도 간 트레이드오프를 고려**
    
    ---
    
    ### Place (실행 전략)
    
    - 출석판 로직을 독립된 기능으로 구성
    - 출석 조건 판단을 서버 코드가 아닌 **기획 데이터 기반 처리**로 전환
    - 출석 상태 저장 및 조회는 빈번한 접근을 고려해 **경량 구조로 설계**
    
    ---
    
    ### Promotion (전달 / 설득)
    
    - 기획팀과 협업하여 출석 규칙을 데이터로 표현할 수 있도록 구조를 설명하고
    - 신규 출석판 추가 시 **서버 수정 없이 기획 데이터만으로 적용 가능함을 공유**
    - 이후 출석 이벤트 및 장기 보상 시스템 설계 시 **공통 시스템으로 재사용 가능함을 제안**
    
    ---
    
    ### [요약]
    
    출석 이벤트의 복잡한 요구사항을 기획 데이터 기반의 범용 시스템으로 재설계하여,
    신규 출석판 추가 시 최소한의 코드 수정으로 대응 가능한 구조를 설계·구현하였습니다.
    또한 출석 이벤트 뿐 아니라 시즌 패스 등 출석 기반 보상 시스템으로 확장 가능한 구조를 구축했습니다.
