제출하신 자기소개서, 포트폴리오, 경력 기술서 내용을 상세히 분석하여 **AI 면접 및 기술/인성 역량 검증에 나올 가능성이 높은 예상 질문 리스트**입니다.

AI 면접 특성상 **"경험의 진위 여부 확인"**, **"기술적 선택의 이유와 트레이드오프"**, **"문제 해결 과정에서의 논리성"**을 집중적으로 검증합니다.

## 2. 직무 및 기술 경험 Deep-Dive (자소서/경력 기반)

### A. 마이크로볼츠 에러 로그 누락 개선 (데이터/DB)
* Bulk Insert 실패 시 `INSERT IGNORE` 대신 `Error Handler` 방식을 선택하여 데이터 정합성을 챙겼다고 하셨습니다. 이로 인해 **오류 발생 시 소폭의 성능 저하**가 발생할 수 있다고 하셨는데, 실제로 서비스에 미친 영향은 어느 정도였으며 이를 완화하기 위한 고려는 무엇이었나요?
* 일 평균 12만 건의 로그가 발생하는 환경에서 DB 파티셔닝 구조를 개선할 때, MySQL 이벤트 프로시저 외에 DB 부하를 줄이기 위해 별도로 고려한 점이 있나요?

### B. 출석판 & 무기 튜닝 시스템 구조 개선 (시스템 설계)
* 출석판 개발 시 **BIGINT 비트 플래그** 방식을 사용해 DB 레코드 수와 조회 부담을 줄였으나, 64일 제한이라는 한계를 언급하셨습니다. 회고에서 제시하신 **문자열/JSON 저장 방식**으로 전환할 경우, DB 인덱싱이나 조회 성능 측면에서 어떤 트레이드오프가 새로 발생할 것이라 생각하시나요?
* 무기 데이터와 튜닝 데이터를 정규화하여 분리하셨습니다. 이 과정에서 무기 조회 시 추가적인 `JOIN`이나 DB 라운드트립이 발생했을 텐데, 이에 따른 성능 영향은 어떻게 해결하셨나요?

### C. 킹스레이드 및 스키드러쉬 등 기타 경험
* 킹스레이드 소탕 시스템 확장 시 Node.js, Docker, Redis 환경을 경험하셨습니다. Redis를 활용할 때 캐시 데이터의 일관성 유지나 메모리 관리에서 중점적으로 고려한 부분은 무엇인가요?
* 건즈 글로벌과 DK온라인에 지원한 '크리에이터 지원 DLL' 개발 시, Steamworks API와 국내 빌링 API 간의 결제 처리 방식 차이를 어떻게 추상화하여 구현하셨나요?

## 3. 포트폴리오 Deep-Dive (TuxBase-MMO 서버 엔진)

### A. RingBuffer 및 Zero-copy 구조
* TCP 스트림 처리를 위한 RingBuffer 설계 시 `Wrap-around` 방식을 **힙 할당 → Scatter-gather → Tail-skip**으로 변경하셨습니다. Tail-skip 방식 적용 시 연속된 메모리 공간 부족으로 인해 발생할 수 있는 파편화 문제나 패킷 처리 지연은 어떻게 다루셨나요?
* RAII 핸들(`RingBufferWriter/Reader`)을 이용해 Zero-copy를 구현하셨는데, 만약 직렬화/역직렬화 도중 예외나 패킷 오염이 발생했을 때 RAII 스코프 탈출 시 commit 처리가 안전하게 롤백되도록 어떻게 보장하셨나요?
* 버퍼 소유권을 `std::unique_ptr<char[]>`에서 `std::array`로 변경하여 힙 할당을 없앤 대신 동적 크기 조절을 포기하셨습니다. 만약 버퍼 고정 크기를 초과하는 대용량 패킷이 수신될 경우 이에 대한 예외 처리 전략은 무엇인가요?

### B. 멀티스레드 및 아키텍처
* **네트워크 I/O 스레드와 컨텐츠 스레드를 분리**하고 `LockQueue`로 전달하는 구조를 채택하셨습니다. 컨텐츠 스레드에서 특정 로직 병목으로 인해 `LockQueue`에 패킷이 계속 쌓여 메모리가 증가하는 상황이 발생한다면 어떻게 대응할 수 있을까요?
* Lock-free Queue 대신 `LockQueue`를 선택하신 이유와, 스레드 간 컨텍스트 스위칭 및 Lock 락 걸림(Contention)으로 인한 오버헤드를 최소화하기 위해 사용한 기법이 있나요?

## 4. 협업, 커뮤니케이션 및 상황 판단 (Situational)
