3. 본인의 장단점을 말씀해주세요.

[예시 답안 - 약 55초]
 [장점] 제 장점은 반복될 기능을 만나면 구조부터 다시 잡는 것입니다. 출석판이 주간, 월간처럼 종류별로 나뉘어 새 출석판마다 서버 코드를 더해야 했던 걸, 어떤 출석판이든 데이터 조합만으로 정의되는 하나의 범용 구조로 바꿨습니다.
 [단점] 다만 같은 작업에서 제 단점도 드러났습니다. 구조를 깔끔하게 만드는 데 집중하느라 데이터를 여러 테이블로 잘게 나눴고, 정작 그 데이터를 넣는 기획자는 출석판 하나를 구성하려고 시트 여러 개를 오가야 했습니다. 기술적으로 깔끔한 구조와 실제로 쓰기 좋은 구조가 다를 수 있다는 걸 그때 배웠고, 이후로는 구조를 확정하기 전에 기획자가 데이터를 어떻게 입력하고 수정하는지부터 확인하고, 잘게 나눌 부분과 한곳에 모을 부분을 구분해 설계합니다.

 - 극복: 구조 확정 전 기획자 입력·수정 흐름부터 확인 / 나눌 부분·모을 부분 구분

4. 지원자께서는 지원하신 직무가 어떤일을 하는지 알고 계신가요?

[예시 답안 - 약 58초]
 게임 서버 프로그래머는 클라이언트가 보내는 요청을 서버에서 검증하고 처리해, 게임의 규칙과 데이터를 지키는 일이라고 이해하고 있습니다.
 크게 셋입니다. 첫째, 콘텐츠 로직을 서버에 구현합니다. 아이템, 재화, 성장 같은 기능을 클라이언트가 아니라 서버가 최종 판정하게 해 비정상 플레이를 막습니다. 둘째, 그 데이터를 담는 DB를 설계하고 트래픽에 맞게 처리 구조를 다듬습니다. 셋째, 라이브에서 장애를 모니터링하고 원인을 분석해 대응합니다.
 저는 마상소프트에서 이 셋을 모두 해왔습니다. C++로 콘텐츠 기능을 개발하고, MySQL로 유저 데이터와 로그 구조를 설계하고, 마이크로볼츠 라이브 주 담당자로 장애 대응을 맡았습니다. 다만 대규모 트래픽을 전제로 한 분산 서버 아키텍처는 아직 경험이 얕아, 그 부분을 넥슨에서 깊게 배우고 싶습니다.

[주요 키워드]
 - 정의: 클라이언트 요청을 서버에서 검증·처리 -> 게임 규칙과 데이터를 지킴
 - 축 1: 콘텐츠 로직을 서버에 구현 / 서버가 최종 판정(server authoritative) -> 비정상 플레이 차단
 - 축 2: 데이터 DB 설계 + 트래픽에 맞게 처리 구조 튜닝
 - 축 3: 라이브 장애 모니터링·원인 분석·대응
 - 경험 증명: C++ 콘텐츠 기능 / MySQL 유저·로그 구조 설계 / 마이크로볼츠 라이브 주 담당 장애 대응
 - 성장 포인트: 대규모 트래픽 분산 서버 아키텍처는 경험 얕음 -> 넥슨에서 배우고 싶음

[암기용 3비트]
 1. 정의: 클라 요청을 서버가 검증·처리해 규칙과 데이터를 지킴
 2. 3축: (1) 콘텐츠 로직(서버가 최종 판정) (2) DB 설계·튜닝 (3) 라이브 장애 대응
 3. 증명 + 성장: 마상소프트에서 셋 다 해봄 / 대규모 분산 아키텍처는 넥슨에서 배우고 싶음

[예상 후속 질문 대비]
 - "분산 서버 아키텍처가 뭔지 아나요?" -> 월드·채널·존 단위로 서버를 나눠 유저를 분산 배치하고, 서버 간 통신은 메시지 큐/RPC, 공유 상태는 Redis 같은 캐시로. 개인 프로젝트에서 네트워크 I/O 스레드와 콘텐츠 처리 스레드를 분리하는 수준까지는 구현해봄
 - "server authoritative가 왜 중요한가요?" -> 클라이언트는 조작될 수 있으니 재화·아이템·좌표 같은 중요한 판정은 서버가 해야 재화 복사·스피드핵 같은 어뷰징을 막음
 - "이 직무에서 제일 자신 있는 부분 / 약한 부분은?" -> 자신: 라이브 장애 대응, 데이터 구조 설계 / 약함: 대규모 트래픽 분산 아키텍처, 부하 테스트

6. 지원자께서는 지원하는 직무를 위해서 어떤 노력을 하셨나요?

[예시 답안 - 약 58초]
 저는 서버팀 인원이 여러 라이브 서비스를 함께 맡는 환경에 있어서, 처음 보는 프로젝트를 빠르게 파악하는 능력을 키우는 데 가장 많이 노력했습니다.
 먼저, 낯선 코드와 기획을 체계적으로 파악하는 저만의 흐름을 만들었습니다. AI 도구를 역할별로 나눠 기획 문서를 요구사항으로 정리하고, 레거시 코드를 분석하고, 작업을 최소 단위로 쪼개 로드맵을 짜는 순서로, 어떤 프로젝트를 맡아도 같은 방식으로 착수하고 있습니다.
 환경이 달라도 마찬가지였습니다. 킹스레이드를 맡았을 때는 C++ 서버만 하던 제가 Node.js와 Redis 기반 환경을 짧은 기간에 익혀 소탕 시스템 확장 기능을 개발했습니다. 새로운 언어나 구조를 만나도 빠르게 적응하는 것이 라이브 서비스 팀에서 제가 길러온 강점입니다.

 - 마무리: 새 언어·구조에도 빠르게 적응 = 라이브 서비스 팀에서 길러온 강점

[암기용 3비트]

7. 지원자께서는 입사후에 하고 싶은 것이 있다면 말씀해주세요.

[예시 답안 - 약 57초]

 그런 엔진은 책상에서 나오지 않습니다. 대규모 MMO를 직접 만들고 오래 운영해본 경험이 있어야 하고, 넥슨은 국내에서 MMORPG를 가장 오래·많이 만들어온 회사라 그 경험을 쌓기에 가장 좋은 곳입니다.

 - 도달점: 신규 프로젝트의 서버 기반 설계 참여

8. 지원자께서는 어떤 상황일때 스트레스를 받으시나요? 그리고 어떻게 푸시나요?

[예시 답안 - 약 55초]
 저는 원인이 잡히지 않는 문제가 길어질 때 스트레스를 받습니다. 장애가 났는데 재현이 안 되거나, 어디서 잘못됐는지 구간이 좁혀지지 않을 때입니다.
 그럴 때는 먼저 잠깐 자리를 떠서 산책하거나 가볍게 운동하며 머리를 식힙니다. 계속 붙잡으면 같은 생각만 반복하게 돼서, 의식적으로 거리를 둡니다.
 그다음 돌아와 문제를 글로 잘게 쪼갭니다. 확인된 것과 아직 모르는 것을 나눠 적으면, 막연하던 문제가 확인할 목록으로 바뀌면서 스트레스도 줄어듭니다. 로그 누락 때도 프로시저 단계를 나눠 원인 구간을 좁혔습니다. 주말에는 게임이나 개인 프로젝트로 완전히 전환합니다.

[주요 키워드]
 - 스트레스 상황: 원인이 안 잡히는 문제가 길어질 때 (재현 안 됨 / 원인 구간 안 좁혀짐)
 - 1단계: 잠깐 자리 뜨고 산책·운동으로 머리 식힘 (같은 생각 반복 차단)
 - 2단계: 문제를 글로 잘게 쪼갬 -> 확인된 것 / 모르는 것 분리 -> 막막함이 확인 목록으로
 - 근거: 로그 누락 때 프로시저 단계를 나눠 원인 구간 축소
 - 완전 전환: 주말엔 게임 / 개인 프로젝트

[암기용 3비트]
 1. 상황: 원인이 안 잡히는 문제가 길어질 때 (재현 안 됨 / 구간 안 좁혀짐)
 2. 해소: (1) 산책·운동으로 거리 두기 (2) 문제를 글로 쪼개 확인된 것/모르는 것 분리 (로그 누락 때처럼)
 3. 전환: 주말엔 게임·개인 프로젝트로 완전 전환

[예상 후속 질문 대비]
 - "주말에도 개발하면 지치지 않나?" -> 실무는 남의 코드에서 원인을 찾는 일, 개인 프로젝트는 처음부터 내가 설계하는 일이라 성격이 달라 오히려 환기가 된다. 그것도 싫으면 그냥 게임을 한다
 - "그 방법으로도 안 풀리면?" -> 혼자 오래 붙잡지 않고 확인한 것·못 한 것을 정리해 팀에 공유하고 도움을 요청한다
 - "팀원과 갈등으로 스트레스 받은 적은?" -> 큰 갈등은 없었다. 의견이 다를 때는 근거를 정리해 대화로 푸는 편 (킹스레이드 챌린지 레이드 사례)


9. 많은 지원자들 가운데 왜 본인을 뽑아야 한다고 생각하시나요?

[암기용 3비트]

[예상 후속 질문 대비]
