1. 이제까지 살아오면서 가장 어려웠던(힘들었던) 경험은 무엇이었나요?

[예시 답안 - 약 45초]
 입사 후 킹스레이드를 맡았을 때가 가장 힘들었습니다. 저는 C++ 서버만 해왔는데, 이 프로젝트는 Node.js와 Redis, Docker 기반이었고 라이브 서비스라 배우면서 동시에 기능을 개발해야 했습니다.
 처음 2주는 코드를 읽어도 구조가 안 그려져 진도가 안 나갔습니다. 그래서 접근을 바꿔, 전체를 이해하려 하지 않고 소탕 시스템 한 흐름만 요청부터 응답까지 따라가며 정리했습니다. 그 한 줄기가 잡히니 나머지가 빠르게 붙었고, 결국 기간 안에 지하던전·길드 레이드로 확장하는 기능을 개발했습니다.
 이때 낯선 환경일수록 전체가 아니라 한 흐름부터 잡아야 한다는 걸 배웠습니다.

[주요 키워드]
 - 상황: 입사 후 킹스레이드 - C++만 하다 Node.js·Redis·Docker, 라이브라 배우며 개발
 - 고비: 첫 2주 구조가 안 그려져 진도 정체
 - 전환: 전체 이해 포기 -> 소탕 시스템 한 흐름만 요청~응답까지 추적
 - 결과: 한 줄기 잡히니 확장, 기간 내 지하던전·길드 레이드 기능 완성
 - 교훈: 낯선 환경일수록 전체가 아니라 한 흐름부터

[암기용 3비트]
 1. 상황 - 킹스레이드, C++만 하다 Node.js 스택, 라이브라 배우며 개발
 2. 고비와 전환 - 첫 2주 정체 -> 소탕 한 흐름만 처음부터 끝까지 추적
 3. 결과·교훈 - 기간 내 확장 완성 / 낯선 환경은 한 흐름부터

[예상 후속 질문 대비]
 - "왜 힘든 게 아니라 못 한다고 안 했나?" -> 못 하겠다고 말하기 전에 접근을 바꿔볼 시간을 스스로 정해두는 편
 - "그 경험이 지금 어떻게 남았나?" -> 이후로 낯선 프로젝트는 무조건 대표 기능 한 흐름부터 훑는 습관이 생김


2. 야근이나 주말출근에 대해 어떻게 생각하나요?

[예시 답안 - 약 30초]
 필요할 때는 하는 게 맞다고 생각합니다. 라이브 서비스는 장애나 런칭처럼 시간을 다투는 일이 있고, 그때 자리를 지키는 건 당연합니다.
 다만 상시가 되면 안 된다고 봅니다. 야근이 기본이 되면 집중력이 떨어져 실수가 늘고, 그게 다시 야근을 부릅니다. 급할 때 몰아서 하고 평소엔 정해진 시간 안에 끝내는 게, 길게 보면 더 안정적으로 기여하는 방법입니다.

[주요 키워드]
 - 수용: 장애·런칭 등 시간 다투는 일엔 당연히 한다
 - 경계: 상시화는 반대 - 집중력 저하 -> 실수 -> 다시 야근의 악순환
 - 지향: 급할 때 몰아서, 평소엔 정시에 끝내기 = 길게 보면 더 안정적 기여

[암기용 2비트]
 1. 필요할 때는 당연 - 장애·런칭
 2. 상시화는 반대 - 실수 늘어 악순환 / 급할 때 몰아서, 평소엔 정시

[예상 후속 질문 대비]
 - "야근이 잦은 팀에 배치되면?" -> 우선 맞춰서 하되, 반복 작업 자동화나 우선순위 조정으로 총량을 줄일 여지를 찾는다
 - "주말에 장애 나면?" -> 담당이면 대응한다. 라이브 서비스는 그게 일의 일부라고 본다


3. 상사와 의견이 다를 때는 어떻게 하실 건가요?

[예시 답안 - 약 30초]
 먼저 상사의 판단에는 제가 못 본 정보가 있을 수 있으니, 왜 그렇게 보시는지부터 묻습니다.
 그다음 제 의견을 근거와 함께 말씀드립니다. 추측이 아니라 코드나 데이터로 얘기하면 대화가 짧아집니다. 그렇게 논의한 뒤에도 결정이 다르면 따릅니다. 다만 서비스에 위험이 될 수 있는 부분이면, 우려한 지점은 기록으로 남겨 공유합니다.

[주요 키워드]
 - 1: 상사 판단의 근거부터 묻기 (내가 못 본 정보 가정)
 - 2: 내 의견은 추측 아닌 코드·데이터로
 - 3: 논의 후에도 결정이 다르면 따름
 - 단서: 서비스 위험 요소면 우려 지점을 기록·공유

[암기용 3비트]
 1. 상사 근거부터 묻기
 2. 내 의견은 코드·데이터로
 3. 그래도 다르면 따르되, 위험 요소는 기록·공유

[예상 후속 질문 대비]
 - "따르기만 하면 소신이 없는 것 아닌가?" -> 근거로 한 번은 분명히 말한다. 그 뒤 결정을 존중하는 것과 소신은 다른 문제
 - "기록으로 남긴다는 게 방어적으로 보이지 않나?" -> 책임 회피가 아니라, 문제가 생겼을 때 빨리 되짚기 위한 것


4. 다른 사람을 배려하고 도움을 제공하여 긍정적인 영향을 주었던 경험에 대해서 말씀해 주세요.

[예시 답안 - 약 40초]
 마이크로볼츠를 담당할 때, 사업팀이 유저 문의를 처리하려면 로그를 봐야 하는데 운영툴에서 로그가 자꾸 비어 보였습니다. 그때마다 사업팀이 저에게 로그를 대신 뽑아달라고 요청했고, CS 답변은 그만큼 밀리고 있었습니다.
 단순 오류로 넘길 수도 있었지만, 사업팀이 계속 저를 거쳐야 하는 상황 자체가 문제라고 봤습니다. 그래서 로그 적재 과정을 파고들어, 파티셔닝 단계에서 일부 로그가 조회되지 않던 구조를 찾아 처리 방식을 바꿨습니다.
 그 뒤로 사업팀은 저를 거치지 않고 직접 로그를 조회하게 됐고, CS 지연도 사라졌습니다. 상대가 나에게 반복해서 부탁하는 상황이 보이면, 그 부탁 자체가 없어지도록 돕는 게 낫다는 걸 배웠습니다.

[주요 키워드]
 - 상황: 사업팀이 CS 처리에 로그가 필요한데 운영툴에서 비어 보임 -> 매번 나에게 대신 조회 요청 -> CS 지연
 - 판단: 단순 오류 아님. 사업팀이 계속 나를 거쳐야 하는 구조 자체가 문제
 - 행동: 요청받은 게 아니라 반복되는 걸 보고 먼저 착수 -> 파티셔닝 단계에서 로그가 조회 안 되던 구조를 찾아 처리 방식 변경
 - 결과: 사업팀이 나 없이 직접 조회 / CS 지연 해소
 - 교훈: 상대가 반복해서 부탁하는 상황이면, 그 부탁이 없어지도록 돕는 게 낫다

[암기용 3비트]
 1. 상황 - 사업팀이 CS용 로그를 못 봐서 매번 나에게 요청, CS 지연
 2. 행동 - 단순 오류로 안 넘기고, 조회 안 되던 파티셔닝 구조까지 파고들어 수정
 3. 결과·교훈 - 사업팀이 직접 조회 가능 / 반복되는 부탁은 부탁 자체를 없애는 게 도움

[예상 후속 질문 대비]
 - "본인 담당 업무였나?" -> 라이브 모니터링·장애 대응이 내 역할이라 담당은 맞지만, 이 건은 요청받은 게 아니라 반복되는 걸 보고 먼저 손댐
 - "기술적으로 어떻게 고쳤나?" -> Bulk Insert가 실패하면 배치 전체가 조회 안 되던 걸, 실패 건만 단건 재삽입하도록 변경 (성능보다 정합성 우선)
 - "사업팀 반응은?" -> 이후 로그 관련해서 먼저 상의가 오는 경우가 늘었고, 수정된 방식이 표준 절차로 자리잡음
 - "자기소개 때 로그 얘기와 겹치지 않나?" -> 같은 사건이지만, 여기서는 사업팀의 반복 요청을 없앤 쪽에 초점 (자기소개는 구조적 원인 분석 쪽)


5. 직업선택시 본인이 가장 중요하게 생각하는것은 무엇인가요?

[예시 답안 - 약 40초]
 저는 함께 일하는 사람을 가장 중요하게 봅니다.
 서버 개발은 혼자 완성하는 일이 아니고, 라이브 서비스는 몇 년을 같은 팀과 붙어 있어야 하는 일입니다. 신뢰할 수 있는 사람들과 일할 때 서로 솔직하게 의견을 내고, 그만큼 결과도 좋아진다고 느껴왔습니다.
 사실 제가 게임에서 가장 좋아하는 장면도 유저들이 서로 관계를 맺고 오래 머무는 모습인데, 제 일도 그런 팀에서 오래 하고 싶습니다. 넥슨은 20년 넘게 한 서비스를 이어온 팀이 여럿 있어, 그게 가능한 곳이라 생각합니다.

[주요 키워드]
 - 1순위: 함께 일하는 사람
 - 이유: 서버 개발은 협업 / 라이브는 수년을 같은 팀과 / 신뢰하는 사람들과 일할 때 솔직한 의견 -> 결과도 좋아짐
 - 정체성 연결: 게임에서 좋아하는 장면 = 유저들이 관계 맺고 오래 머무는 모습 -> 내 일도 그런 팀에서 오래
 - 회사 착지: 넥슨 = 20년+ 한 서비스를 이어온 팀 다수 -> 오래 함께 일할 수 있음

[암기용 3비트]
 1. 1순위 - 함께 일하는 사람
 2. 이유 - 라이브는 수년을 같은 팀과 / 신뢰하는 사람들과여야 솔직한 의견, 좋은 결과
 3. 연결·착지 - 유저들이 관계 맺는 모습을 좋아하듯 나도 그런 팀에서 오래 / 넥슨엔 그런 팀이 여럿

[예상 후속 질문 대비]
 - "사람만 좋으면 일이 지루해도 괜찮나?" -> 아니다. 좋은 사람들과는 지루한 구간도 같이 넘긴다. 반대로 일이 재밌어도 팀이 무너지면 오래 못 간다
 - "그다음으로 중요한 건?" -> 이유를 이해하고 구조를 직접 설계할 수 있는 환경. 배경 설명 없이 일단 만들라는 방식은 잘 안 맞는다
 - "함께 일하고 싶은 사람은?" -> 근거로 대화하는 사람, 문제를 숨기지 않는 사람
 - "인간관계로 이직 고려한 적 있나?" -> 없다. 오히려 사람 때문에 지금 회사를 다니고 있다


6. 상사가 부당한 업무를 지시했을때는 어떻게 행동하실건가요?

[예시 답안 - 약 32초]
 부당하다고 느낀 게 판단 차이인지, 규정이나 윤리에 어긋나는 문제인지 먼저 구분합니다.
 판단 차이라면 지시 의도를 확인하고 제 우려를 근거와 함께 다시 말씀드린 뒤, 그래도 같은 지시면 제가 못 본 맥락이 있다고 보고 따르되 리스크는 기록해 둡니다. 규정이나 윤리 문제라면 따르지 않고 정식 경로로 제기하겠습니다.

[주요 키워드]
 - 1단계: 구분 - 판단 차이 vs 규정·윤리 위반
 - 판단 차이: 의도 확인 -> 근거로 재의견 -> 그래도면 따르되 리스크 기록
 - 위반: 따르지 않고 정식 경로

[암기용 2비트]
 1. 구분 - 판단 차이냐 규정·윤리냐
 2. 판단 차이는 근거로 재의견 후 따르되 기록 / 위반은 정식 경로로 거부

[예상 후속 질문 대비]
 - (상황질문 7번과 동일 프레임 - 팀원 대상이든 상사 대상이든 같은 기준으로 답)
 - "부당한지 애매하면?" -> 혼자 판단하지 않고 동료·선배 의견을 먼저 들어본다


7. 5년 후에는 어떤모습일지 생각해본적 있나요?

[예시 답안 - 약 38초]
 5년 뒤에는 맡은 프로젝트의 서버에서, 장애 대응만이 아니라 구조를 개선하는 결정을 주도적으로 내리는 사람이 되어 있고 싶습니다. 새 콘텐츠가 들어올 때 어디를 어떻게 바꿔야 할지 판단하고 제안하는 위치입니다.
 길게는, 윈도우와 리눅스 양쪽에서 돌아가는 게임 서버 엔진을 만드는 게 목표입니다. 그건 대규모 MMO를 오래 운영해본 경험이 있어야 가능하고, 넥슨에서 그 경험을 쌓는 5년이 되길 바랍니다.

[주요 키워드]
 - 5년 상: 맡은 프로젝트 서버에서 구조 개선 결정을 주도 / 새 콘텐츠 들어올 때 어디를 어떻게 바꿀지 판단·제안
 - 장기: 윈도우·리눅스 크로스플랫폼 게임 서버 엔진
 - 넥슨 연결: 그 엔진은 대규모 MMO를 오래 운영해봐야 가능 -> 그 경험을 쌓는 5년

[암기용 3비트]
 1. 5년 - 맡은 서버의 구조 개선을 주도적으로 판단·제안하는 사람
 2. 장기 - 윈도우·리눅스 서버 엔진
 3. 연결 - 대규모 MMO 운영 경험이 있어야 가능, 그걸 넥슨에서

[예상 후속 질문 대비]
 - "5년 안에 팀장이 되고 싶나?" -> 직책보다, 서버 구조를 책임지고 판단하는 역할이 목표. 그 과정에서 리드를 맡게 되면 한다
 - "그 엔진 목표가 회사와 안 맞으면?" -> 회사 안에서 대규모 서버를 설계·운영하는 경험 자체가 그 목표와 같은 방향이라 충돌하지 않는다


8. 개인의 전문성 향상과 팀의 협업 능력 향상 중에서 더 우선시해야 한다고 생각하는 것과 이유를 말씀해주세요.

[예시 답안 - 약 38초]
 저는 팀의 협업 능력이 먼저라고 생각합니다. 개인 실력은 아무리 뛰어나도 혼자 감당할 수 있는 범위가 정해져 있는데, 팀이 잘 맞물리면 그 한계를 넘습니다.
 특히 제가 있는 팀은 적은 인원이 여러 서비스를 나눠 맡고 있어서, 한 사람만 아는 코드나 구조가 생기면 그게 곧 팀의 약점이 됩니다. 그래서 내가 잘하는 것만큼, 내가 아는 걸 남이 이어받을 수 있게 만드는 게 중요합니다.
 물론 개인 전문성도 계속 키워야 하지만, 우선순위를 하나 꼽으면 팀 쪽입니다.

[주요 키워드]
 - 선택: 팀 협업 능력 우선
 - 이유 1: 개인 실력은 혼자 감당 범위가 정해짐 / 팀이 맞물리면 그 한계를 넘음
 - 이유 2: 적은 인원이 여러 서비스 분담 -> 한 사람만 아는 코드·구조 = 팀의 약점
 - 균형: 개인 전문성도 계속 키움 - "내가 잘하는 것" + "내가 아는 걸 남이 이어받게 만드는 것"

[암기용 2비트]
 1. 팀 협업 우선 - 개인 실력엔 감당 범위 한계, 팀이 맞물리면 그걸 넘음
 2. 근거 - 적은 인원 여러 서비스 / 혼자만 아는 구조 = 팀 약점 -> 이어받게 만드는 게 중요

[예상 후속 질문 대비]
 - "개인 실력이 약해도 협업만 잘하면 되나?" -> 아니다. 각자 실력이 전제. 실력을 팀에 어떻게 연결하느냐가 우선순위라는 뜻
 - "본인은 협업형인가?" -> 구조 설계는 혼자 파고드는 걸 좋아하지만, 그 결과물은 남이 쓸 수 있어야 의미가 있다고 본다
 - "협업 능력은 어떻게 키우나?" -> 문서화, 코드 리뷰에서 의도를 남기기, 남이 물어보기 전에 구조를 설명해 두기


9. 지원자께서는 어떤사람과 일하고 싶지 않은가요? 그 사람과 일하게 된다면 어떻게 하실건가요?

[예시 답안 - 약 38초]
 자기가 하던 일을 넘길 때 인수인계를 제대로 안 하는 사람과 일하면 힘듭니다. 문서도 없고 까다로운 부분 설명도 없이, 코드 보면 된다로 끝내는 경우입니다. 저희 팀은 적은 인원이 여러 서비스를 돌아가며 맡아서 인수인계가 자주 일어나는데, 이게 부실하면 다음 사람이 몇 주를 헤맵니다.
 그런 상황이면, 넘겨받을 때 코드만 보지 않고 대표 기능 하나를 요청부터 응답까지 같이 따라가며 궁금한 걸 목록으로 정리해 묻습니다. 그리고 제가 넘길 때는, 남이 겪을 걸 아니까 자주 막히는 지점과 배경을 문서로 남깁니다.

[주요 키워드]
 - 싫은 유형: 인수인계를 제대로 안 하는 사람 (문서·설명 없이 "코드 보면 된다")
 - 이유: 적은 인원이 여러 서비스 돌아가며 담당 -> 인수인계 잦음 -> 부실하면 다음 사람이 몇 주 헤맴
 - 대처(받을 때): 코드만 X, 대표 기능 하나를 요청~응답까지 같이 추적 / 궁금한 것 목록화해 질문
 - 대처(넘길 때): 남이 겪을 걸 아니까 자주 막히는 지점·배경을 문서로 남김

[암기용 3비트]
 1. 싫은 유형 - 인수인계 부실 ("코드 보면 돼요")
 2. 이유 - 적은 인원 여러 서비스, 인계 잦음 -> 부실하면 다음 사람 몇 주 낭비
 3. 대처 - 받을 땐 대표 기능 한 줄기 같이 추적 + 질문 목록 / 넘길 땐 막히는 지점 문서화

[예상 후속 질문 대비]
 - "인수인계 문서가 없으면 일을 못 하나?" -> 아니다. 없으면 파악하면서 내가 만든다. 다만 있으면 팀 전체가 빠르다
 - "낯선 프로젝트를 어떻게 파악하나?" -> 전체를 한 번에 보지 않고 대표 기능 한 흐름부터. AI로 기획 문서를 요구사항으로 정리하고 레거시를 분석하는 흐름도 만들어 뒀다
 - "본인이 인계할 때 실제로 문서를 남긴 사례는?" -> (면접 전 구체 사례 하나 준비 - 실제로 넘긴 서비스/기능 이름과 남긴 문서 형태)


10. 주변사람들은 지원자를 어떻게 평가하나요?

[예시 답안 - 약 42초]
 직접 들은 평가는 많지 않아서, 제가 일하는 모습으로 짐작해 말씀드리겠습니다.
 하나는 걱정이 많다는 겁니다. 배포 전에 뭐가 잘못될 수 있는지부터 떠올려서, 신중하다는 인상을 줄 것 같습니다. 라이브 서비스에선 이게 도움이 됩니다.
 또 하나는 남한테 폐 끼치는 걸 싫어해서, 맡은 일은 끝까지 제가 처리하려 한다는 겁니다. 일이 몰려도 조용히 마무리하는 편이지만, 혼자 떠안다 공유가 늦을 때가 있어 지금은 일찍 알리려 합니다.
 말도 조심하는 편이라, 근거 없이는 잘 단정하지 않습니다.

[주요 키워드]
 - 전제: 직접 들은 평가는 적음 -> 일하는 모습으로 짐작
 - 1) 걱정 많음 -> 배포 전 리스크부터 떠올림 -> 신중하다는 인상 / 라이브에 도움
 - 2) 남에게 폐 끼치기 싫음 -> 맡은 일 끝까지 처리, 몰려도 조용히 마무리 / 단점: 혼자 떠안다 공유 늦음 -> 지금은 일찍 공유
 - 3) 말을 조심함 -> 근거 없이 단정 안 함

[암기용 3비트]
 1. 전제 - 직접 들은 건 적음, 일하는 모습으로 짐작
 2. 걱정 많음 -> 배포 전 리스크부터 (신중, 라이브에 유리)
 3. 폐 끼치기 싫음 -> 끝까지 처리 (단, 혼자 떠안다 공유 늦음 -> 일찍 공유) + 말 조심 -> 근거 없이 단정 안 함

[예상 후속 질문 대비]
 - "걱정이 많으면 결정이 느리지 않나?" -> 배포·데이터처럼 되돌리기 어려운 것만 신중하게 본다. 되돌릴 수 있는 건 빨리 시도한다
 - "혼자 떠안는 게 팀에 문제 된 적은?" -> 진행 상황 공유가 늦어 팀이 늦게 안 적이 있다. 그 뒤로 확인된 것·안 된 것을 짧게 자주 공유한다
 - "말을 조심한다는 게 소극적인 것 아닌가?" -> 반대 의견도 낸다. 다만 근거를 확인한 뒤에 말하는 편 (킹스레이드 챌린지 레이드)
