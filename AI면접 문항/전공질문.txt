4. 개발하면서 가장 기억에 남는 문제나 버그를 어떻게 해결하셨는지 과정을 설명해주세요.

 마이크로볼츠에서 운영툴 로그가 하루 12만 건씩 비어 보이던 문제가 가장 기억에 남습니다.

 - 해결: 정합성 우선 -> Bulk Insert 실패 시 단건 재삽입 / 이후 1년 재발 없음

[암기용 3비트]
 1. 증상·확인 - 로그 12만 건 누락처럼 보임 / 데이터는 오류 테이블에 있었음

6. 프로젝트에서 성능을 개선하거나 최적화를 시도해본 경험이 있나요?

[예시 답안 - 약 50초]
 개인 서버 엔진에서 수신 버퍼를 개선한 경험이 있습니다.
 처음에는 소켓에서 받은 데이터를 버퍼에 넣고, 패킷을 처리할 때 다시 별도 메모리로 복사해서 넘겼습니다. 패킷마다 복사가 반복되는 게 부담이라, 버퍼 내부 메모리를 직접 가리키는 핸들을 만들어 복사 없이 읽고 쓰도록 바꿨습니다.
 버퍼가 원형이라 끝을 넘어가는 경우가 문제였는데, 처음엔 임시 메모리를 할당해 해결하다가, 할당 자체를 없애려고 남은 꼬리 공간을 건너뛰고 앞에서 다시 쓰는 방식으로 세 번에 걸쳐 고쳤습니다.
 회사에서도 출석 데이터를 여러 줄에서 한 줄의 비트 값으로 바꿔, 레코드 수와 조회 부담을 줄인 적이 있습니다.

[주요 키워드]
 - 개인: 수신 버퍼 복사 제거 - 별도 버퍼 복사 -> 내부 메모리를 직접 가리키는 핸들(zero-copy)
 - wrap-around 개선 3회: 임시 힙 할당 -> scatter-gather -> 꼬리 공간 건너뛰고 앞에서 재사용(tail-skip), 할당 자체 제거
 - 회사: 출석 데이터를 다중 레코드 -> 단일 비트 값 -> 레코드 수·조회 부담 감소

[암기용 3비트]
 1. 수신 버퍼 - 복사 넘김 -> 내부 메모리 직접 접근(zero-copy)
 2. wrap-around - 힙 할당 -> tail-skip으로 할당 제거 (3회 개선)
 3. 회사 - 출석 데이터 다중 레코드 -> 단일 비트 값

[예상 후속 질문 대비]
 - "성능을 수치로 측정했나?" -> 개인 프로젝트는 아직 부하 테스트 단계 전이라, 복사·할당 횟수 감소 같은 구조적 개선 중심이다. 측정 기반 최적화는 앞으로 보완할 부분
 - "tail-skip의 단점은?" -> 연속 공간이 부족하면 요청 크기를 한 번에 못 준다. 그래서 읽기는 연속 접근 가능한 만큼만 반환하고 호출부가 다시 요청하게 설계했다
 - "최적화하다 과하게 복잡해진 적은?" -> scatter-gather 방식이 호출부에서 두 조각을 따로 처리해야 해 복잡했다. 그래서 tail-skip으로 바꿨다


7. 팀원과 의견이 다르거나 갈등이 있었을 때 어떻게 해결하셨나요?

[예시 답안 - 약 48초]
 킹스레이드에서 소탕 시스템을 개발할 때, 챌린지 레이드에도 소탕 기능을 넣어 달라는 기획 요청을 받았습니다. 저는 좀 이상하다고 느껴서 바로 구현하지 않고, 챌린지 레이드의 코드와 구조를 먼저 봤습니다.
 확인해 보니 이 콘텐츠는 재화를 얻는 게 아니라 기록을 경신하는 게 목적이었습니다. 실제로 플레이하지 않고 보상만 받는 소탕은 이 콘텐츠 목적과 안 맞았습니다.
 그래서 그냥 반대한다고 하지 않고, 제가 분석한 구조를 같이 보여주면서 왜 안 맞는지 설명했습니다. 기획자도 수긍했고, 그 기능은 최종적으로 빠졌습니다. 요청을 그대로 만들기보다 근거를 확인해 의견을 내는 게, 불필요한 개발을 막는다는 걸 배웠습니다.

[주요 키워드]
 - 상황: 챌린지 레이드에도 소탕 기능 추가 요청
 - 행동: 바로 구현 X -> 챌린지 레이드 코드·구조 직접 분석
 - 근거: 이 콘텐츠 목적 = 재화 획득이 아니라 기록 경신 -> 플레이 없이 보상만 받는 소탕과 부적합
 - 방식: 단순 반대 X -> 분석한 구조를 함께 보여주며 설명 -> 기획자 수긍, 기능 제외
 - 교훈: 근거 기반으로 의견을 내면 불필요한 개발을 막는다

[암기용 3비트]
 1. 요청 - 챌린지 레이드에 소탕 추가
 2. 확인 - 코드 보니 목적이 기록 경신 -> 소탕과 안 맞음
 3. 해결 - 분석 근거를 같이 보여주며 설명 -> 수긍, 기능 제외

[예상 후속 질문 대비]
 - "기획자가 끝까지 고집했다면?" -> 최종 결정은 기획 몫이라 따랐을 것. 대신 우려 지점은 기록으로 남겼을 것
 - "매번 이렇게 분석하면 느리지 않나?" -> 모든 요청이 아니라, 구조와 안 맞아 보이는 것만. 초반에 확인하는 게 만들고 되돌리는 것보다 빠르다
 - "감정적으로 부딪힌 적은?" -> 큰 갈등은 없었다. 의견이 다를 때 근거를 정리해 대화로 푸는 편이다


8. 현재 사용하고 있는 기술 스택을 상중하로 평가한다면 어떻게 되고, 부족한 부분은 어떻게 보완하고 계신가요?

[예시 답안 - 약 50초]
 상은 C++와 MySQL입니다. 실무에서 서버 콘텐츠를 C++로 개발했고, MySQL은 프로시저와 파티셔닝, 데이터 구조 설계까지 다뤘습니다. 라이브 장애 대응도 여기 넣겠습니다.
 중은 Linux 운영, 그리고 Node.js와 Redis, Docker입니다. 킹스레이드에서 실무로 썼지만 깊이는 더 필요합니다. 네트워크와 멀티스레드도 개인 프로젝트 수준이라 중입니다.
 하는 대규모 트래픽을 전제로 한 분산 서버 아키텍처와 부하 테스트입니다.
 보완은, 개인 서버 엔진을 만들며 네트워크와 스레드 계층을 직접 구현하고, 막히면 운영체제와 네트워크 기초로 되짚어 가며 채우고 있습니다.

[주요 키워드]
 - 상: C++, MySQL(프로시저·파티셔닝·설계), 라이브 장애 대응
 - 중: Linux 운영 / Node.js·Redis·Docker (킹스레이드 실무, 깊이는 더 필요) / 네트워크·멀티스레드 (개인 프로젝트 수준)
 - 하: 대규모 트래픽 분산 아키텍처, 부하 테스트
 - 보완: 개인 서버 엔진으로 네트워크·스레드 직접 구현 + OS·네트워크 기초로 되짚기

[암기용 3비트]
 1. 상 - C++, MySQL, 라이브 장애 대응
 2. 중 - Linux 운영 / Node·Redis·Docker / 네트워크·스레드(개인 수준)
 3. 하 - 분산 아키텍처·부하 테스트 -> 개인 엔진 + 기초 학습으로 보완

[예상 후속 질문 대비]
 - "분산 아키텍처를 설명할 수 있나?" -> 월드·채널·존 단위로 서버를 나눠 유저를 분산하고, 서버 간은 메시지 큐/RPC, 공유 상태는 Redis 같은 캐시로. 개인 프로젝트에선 I/O 스레드와 콘텐츠 스레드 분리 수준까지 구현
 - "부하 테스트 경험이 없다는 건가?" -> 실무에서 직접 설계해본 적은 없다. 개인 엔진에 부하 테스트를 붙이는 걸 다음 과제로 두고 있다
 - "C#은?" -> 학생 때 유니티로 개인 게임을 만들며 썼다. 지금은 하로 본다


9. 비전공자(또는 전공자)로서 개발 분야에서 본인만의 강점은 무엇이라고 생각하시나요?

[예시 답안 - 약 45초]   [확인 필요 - 전공자 가정]
 전공에서 자료구조나 네트워크, 운영체제 같은 기초를 배웠는데, 제 강점은 거기에 실제 라이브 서비스 경험이 더해진 점입니다.

[암기용 3비트]

10. 앞으로 개발자로서 어떤 방향으로 성장하고 싶고, 그를 위해 어떤 노력을 하고 계신가요?

[예시 답안 - 약 45초]
 저는 게임 서버의 밑단부터 위까지 다 아는 개발자가 되고 싶습니다. 콘텐츠 로직은 실무에서 해왔으니, 그 아래 네트워크와 분산 구조를 같은 깊이로 다루는 게 다음 목표입니다.
 길게는, 윈도우와 리눅스 양쪽에서 도는 게임 서버 엔진을 만들어 여러 개발사가 MMO를 더 쉽게 만들 수 있게 하고 싶습니다.
 그래서 지금은 Boost.Asio로 서버 엔진을 직접 만들며 네트워크 I/O와 버퍼, 멀티스레드 구조를 손으로 구현하고 있고, 막히는 부분은 운영체제와 네트워크 기초로 되짚어 공부하고 있습니다.

[주요 키워드]
 - 방향: 게임 서버의 밑단(네트워크·분산)부터 위(콘텐츠)까지 다 아는 개발자
 - 다음 목표: 콘텐츠는 실무 경험 O -> 그 아래 네트워크·분산 구조를 같은 깊이로
 - 장기: 윈도우·리눅스 크로스플랫폼 게임 서버 엔진 -> 개발사들이 MMO를 쉽게
 - 노력: Boost.Asio 서버 엔진 직접 구현 (I/O·버퍼·멀티스레드) + OS·네트워크 기초 되짚기

[암기용 3비트]
 1. 방향 - 서버의 밑단부터 위까지 다 아는 개발자
 2. 장기 - 크로스플랫폼 게임 서버 엔진 -> MMO를 쉽게
 3. 노력 - Boost.Asio 엔진 직접 구현 + 기초 학습

[예상 후속 질문 대비]
 - "그 엔진을 넥슨에서 만들 수 있다고 보나?" -> 당장은 아니다. 대규모 MMO를 설계·운영해본 경험이 먼저 필요하고, 그 경험을 쌓기에 넥슨이 가장 좋은 곳이라 생각한다
 - "5년 뒤 구체적인 모습은?" -> 맡은 프로젝트의 서버 구조를 책임지고, 장애 대응만이 아니라 개선 방향을 판단·제안하는 위치
 - "성장을 위해 읽는 자료나 공부 방식은?" -> 운영체제·네트워크 기본서로 되짚고, 만들다 막힌 지점을 중심으로 파고드는 방식
