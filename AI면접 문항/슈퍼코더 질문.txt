"누가 시키지 않았는데 스스로 시작해 끝까지 해낸 일" (주도성)
저는 회사 업무와 별개로 게임 서버 엔진을 직접 만들어보고 싶어서, 아무도 시키지 않은 개인 프로젝트를 시작했습니다.
목표는 네트워크 I/O와 버퍼 자료구조, 스레드 구조 같은 서버의 밑바닥을 처음부터 구현해보는 것이었습니다. 수신 버퍼를 복사 없이 처리하도록 세 번에 걸쳐 고쳐 나갔고, 네트워크 I/O 스레드와 콘텐츠 처리 스레드를 분리하는 구조까지 완성했습니다.
회사 일과 병행하느라 시간 내기가 쉽지 않았지만, 퇴근 후나 주말에 조금씩 계속 진행해서 처음 목표했던 핵심 계층은 끝까지 구현해냈습니다.

A. 기술 세부사항 파고들기
	1. "zero-copy가 정확히 뭔가요? 왜 필요했나요?" → 패킷 처리 때마다 별도 버퍼로 복사하던 걸, RingBuffer 내부 메모리를 직접 가리키는 RAII 핸들로 읽고 쓰게 해서 복사를 없앰
	2. "wrap-around를 세 번 고쳤다는데, 각각 왜 실패했나요?" → 1차 임시 힙 할당(할당·해제 부담) → 2차 scatter-gather(호출부가 두 조각을 나눠 처리해야 해 복잡) → 3차 tail-skip(할당 없이 앞에서 재사용, 대신 한 번에 다 못 읽을 수 있어 호출부가 재요청)
	3. "왜 Boost.Asio를 썼나요? 직접 소켓 API를 안 쓴 이유는?" → [준비 필요]
	4. "I/O 스레드와 콘텐츠 스레드를 왜 분리했나요?" → I/O 처리 시간이 콘텐츠 로직 처리와 얽히지 않게 하려고. 완성된 Packet만 LockQueue로 안전하게 전달
	5. "두 스레드 사이 동시성 문제(경쟁 상태)는 어떻게 처리했나요?" → LockQueue로 스레드 간 전달 — [구체 락 전략 준비 필요]
	6. "테스트는 어떻게 검증했나요?" → GTest로 wrap-around 같은 경계 조건(read/write 커서 꼬임) 시나리오 작성

B. 동기·심리
	7. "왜 회사 일과 무관한 걸 굳이 주말·퇴근 후에 하나요?" → 회사에선 콘텐츠 계층만 다뤄서, 그 아래 네트워크·스레드 계층을 직접 다뤄보고 싶었다 (심화 2·기본 8 워라밸 답변과 톤 맞출 것)
	8. "완성이 보장 안 되는데 동기부여는 어디서 나오나요?" → [준비 필요 — 진짜 이유 정리]

C. 진행 상황·완결성
	9. "지금 얼마나 진행됐고 언제 완성되나요?" → 2026.03~05 진행, 이후 재개 예정. 인프라(네트워크·버퍼·스레드) 계층은 완성, 콘텐츠 계층은 다음 단계
	10. "왜 중간에 멈췄나요? (재개 예정이라 했는데)" → [준비 필요 — 실제 사유. 면접에서 나오면 얼버무리면 안 되는 지점]

D. 회의적/압박성
	11. "이미 상용 서버 미들웨어가 많은데 왜 굳이 직접 만드나요?" → 가져다 쓰는 것과 내부 동작 원리를 이해하는 건 다르다. 나중에 문제가 생겼을 때 원인을 알려면 밑단을 이해해야 한다고 생각
	12. "이걸 실제로 라이브 서비스에 쓸 계획인가요?" → 아직은 학습·검증 목적. 장기적으로는 기본 7·전공 10번의 크로스플랫폼 엔진 비전과 연결됨

E. 직무 연결
	13. "이 경험이 넥슨 업무에 실제로 도움이 되나요?" → 전공 8번 약점(대규모 분산 아키텍처 경험 얕음)을 이 프로젝트로 보완 중이라는 연결
	14. "이 프로젝트에서 가장 어려웠던 순간은?" → wrap-around 경계 조건에서 read/write 커서 계산이 꼬였던 버그 (전공 4번 후속과 겹치니 표현 다르게)

"계획이 틀어졌던 순간이 있었나요? 그때 실제로 어떻게 했어요?" (문제해결)

[예시 답안 - 약 42초]

출석 시스템을 범용 구조로 설계할 때, 저는 데이터를 최대한 정규화하는 게 맞다고 생각했습니다. 출석판 정의, 조건, 보상, 유저 상태를 각각 별도 테이블로 나눴습니다.

그런데 막상 기획자가 출석판 하나를 만들려면 여러 테이블을 오가며 값을 채워야 했고, 오히려 불편해했습니다. 깔끔한 구조라고 생각했던 계획이, 실제로 쓰는 사람 입장에서는 틀어진 셈이었습니다.

그래서 그 즉시 기획자가 데이터를 어떻게 입력하고 수정하는지부터 다시 확인했고, 이후로는 데이터를 잘게 나눌 부분과 한곳에 모을 부분을 구분해서 설계하는 방식으로 바꿨습니다.

[주요 키워드]

- 계획: 출석 데이터를 최대한 정규화 → 정의·조건·보상·유저상태 각각 별도 테이블
- 틀어짐: 기획자가 출석판 하나 만들려면 여러 테이블을 오가야 해서 불편해함 (예상 못한 결과)
- 대응: 즉시 기획자의 입력·수정 흐름부터 재확인
- 개선: 나눌 부분·모을 부분을 구분해서 재설계

[암기용 3비트]

1. 계획 — 데이터 최대 정규화, 테이블 여러 개로 분리
2. 틀어짐 — 기획자가 여러 테이블 오가야 해서 불편 (예상 밖 결과)
3. 대응 — 입력 흐름 재확인 → 나눌 것·모을 것 구분해서 재설계

[예상 후속 질문 대비]

- "왜 처음부터 기획자 입장을 안 물어봤나?" → 기술적으로 옳은 구조가 곧 좋은 구조라고 생각했다. 이 일로 그 둘이 다를 수 있다는 걸 배웠다
- "지금은 매번 미리 확인하나?" → 그렇다. 구조를 확정하기 전에 데이터를 입력·수정할 사람의 흐름부터 먼저 물어본다
- "이거 말고 계획이 틀어진 다른 사례는?" → 개인 서버 엔진에서 원형 버퍼의 wrap-around 처리 방식을 세 번 바꾼 것도 비슷한 사례다 (기술적으로 더 깊이 들어가고 싶으면 이쪽으로 유도 가능)
- "완전히 다시 만들어야 했나?" → 아니다. 테이블 구조 자체보다 조회·입력 방식을 보완하는 선에서 해결했다. 다만 조건 모듈은 이후 JSON 기반으로 확장하는 개선안을 따로 정리해뒀다

"동료와 의견이 크게 부딪혔을 때, 어떻게 풀었나요?" (협업)

[예시 답안 - 약 44초]

솔직히 감정적으로 크게 부딪힌 적은 없습니다. 다만 의견이 가장 크게 갈렸던 건, 킹스레이드에서 챌린지 레이드에도 소탕 기능을 넣어 달라는 요청을 받았을 때입니다.

기획자는 필요하다고 봤고, 저는 콘텐츠 구조상 안 맞는다고 느꼈습니다. 그 자리에서 반박하지 않고 먼저 코드와 구조를 분석했더니, 이 콘텐츠는 기록 경신이 목적이라 플레이 없이 보상만 받는 소탕은 맞지 않는다는 근거가 나왔습니다. 그걸 보여드리며 설명했고, 기획자도 수긍해 기능은 빠졌습니다.

의견이 갈릴 때 감정보다 근거를 먼저 맞추면, 대부분 크게 번지지 않고 풀린다고 생각합니다.

[주요 키워드]

- 솔직한 전제: 감정적으로 크게 부딪힌 적 없음 → 가장 크게 갈린 사례 = 챌린지 레이드 건
- 상황: 기획자는 소탕 기능 필요하다고 봄 / 나는 콘텐츠 구조상 안 맞는다고 느낌
- 행동: 반박 대신 코드·구조 먼저 분석 → 콘텐츠 목적(기록 경신) 확인 → 근거로 설명
- 결과·철학: 기획자 수긍, 기능 제외 / 감정보다 근거를 먼저 맞추면 대부분 크게 안 번짐

[암기용 3비트]

1. 전제 — 크게 부딪힌 적 없음, 가장 갈린 게 챌린지 레이드 건
2. 행동 — 반박 대신 코드·구조 분석 → 근거(기록경신 목적) 확보 → 설명
3. 결과·철학 — 기획자 수긍, 기능 제외 / 근거를 먼저 맞추면 안 번짐

[예상 후속 질문 대비]

- "정말 한 번도 감정 상한 적 없나?" → 서운한 정도는 있었지만, 근거로 풀리고 나면 대부분 남지 않았다
- "근거로도 안 풀리면 어떻게 하나?" → 팀장에게 판단 기준을 요청해 다시 논의한다 (상황 2번과 연결)
- "기획자가 끝까지 고집했다면?" → 최종 결정은 기획 몫이니 따랐을 것. 대신 우려 지점은 기록해 남겼을 것
- "부딪힘 자체를 회피하는 성향 아닌가?" → 회피가 아니라 조기에 근거로 정렬시키는 방식. 필요하면 반대 의견도 분명히 낸다

"최근 새로 익혀야 했던 것은요? 어떻게 익혔어요?" (재작성안 — Docker)

최근에는 Docker를 실제로 써보면서 익혔습니다. 킹스레이드 프로젝트에서 Docker 기반 환경을 처음 접했는데, 그때는 이미 세팅된 환경 위에서 개발만 했습니다.

그 뒤로 개인 서버 엔진을 만들면서, 이번엔 제가 직접 Docker로 개발·빌드 환경을 구성해봤습니다. 윈도우에서 코드를 짜고 리눅스 컨테이너 안에서 빌드하고 실행하는 구조를 스스로 세팅하면서, 왜 컨테이너로 환경을 맞추는 게 필요한지 체감했습니다.

다만 컨테이너가 내부적으로 어떻게 프로세스를 격리하는지 같은 원리까지는 아직 깊게 알지 못하고, 실제로 쓰는 수준에서 익혔습니다.

[주요 키워드]

- 익힌 것: Docker — 킹스레이드에서 접함(이미 세팅된 환경) → 개인 프로젝트에서 직접 구성해보며 체득
- 방법: 윈도우에서 작성, 리눅스 컨테이너에서 빌드·실행하는 구조를 스스로 세팅
- 정직한 경계: 컨테이너 내부 격리 원리까지는 모름 — 실사용 수준

[암기용 3비트]

1. 계기 — 킹스레이드에서 접함(세팅된 환경) → 보며 체득
2. 방법 — 윈도우 작성/리눅스 컨테이너 빌드·실행 구조를 스스로 세팅
3. 정직한 경계 — 내부 원리(격리 메커니즘)는 모름, 실사용 수준

[예상 후속 질문 대비]

- "Docker와 가상머신 차이는?" → OS를 통째로 안 띄우고 프로세스만 격리해서 더 가볍다는 정도로 알고 있다 (그 이상 세부는 정직하게 "거기까진 깊게 못 봤다"로)
- "왜 컨테이너가 필요했나?" → 로컬(윈도우)과 실행 환경(리눅스)이 달라서, 빌드·실행 결과가 항상 같게 하려고
- "더 깊이 알아야 한다고 느끼나?" → 그렇다. 지금은 쓰는 데 문제없는 수준이고, 필요해지면 원리 쪽도 채울 계획이다

"가장 아쉬웠던 결과는요? 다시 한다면 뭘 바꾸겠어요?" (회고)

[예시 답안 - 약 42초]

출석판을 범용 구조로 만들 때, 출석판마다 다른 고유 동작은 enum으로 구분해서 처리했습니다. 그런데 그러다 보니, 기존에 없던 새로운 유형의 조건이 필요해지면 데이터만으로는 안 되고 서버 코드도 같이 고쳐야 했습니다. 범용 구조라고 했지만 완전히 유연하진 않았던 셈이라, 그게 가장 아쉬운 부분입니다.

다시 한다면, 조건을 enum이 아니라 JSON 같은 구조화된 데이터로 정의해서 모듈과 인자까지 데이터만으로 확장할 수 있게 만들 겁니다. 실제로 이후 킹스레이드에서 그런 방식을 보고, 그게 더 나은 방향이라는 걸 확인했습니다.

[주요 키워드]

- 아쉬운 결과: 출석판을 범용 구조로 만들었지만, 고유 동작을 enum으로 구분 → 새 조건 유형 필요 시 데이터만으로 안 되고 서버 코드도 수정 필요
- 다시 한다면: enum 대신 JSON 같은 구조화 데이터로 모듈·인자까지 정의 → 완전히 데이터 기반 확장
- 근거: 이후 킹스레이드에서 그런 방식을 실제로 봄 → 더 나은 방향 확인

[암기용 3비트]

1. 아쉬움 — 범용 구조라 했지만 고유 동작은 enum, 새 조건은 서버 코드도 수정해야 함
2. 다시 한다면 — JSON으로 모듈·인자까지 데이터화
3. 근거 — 킹스레이드에서 그 방식을 실제로 보고 확인

[예상 후속 질문 대비]

- "그럼 지금 그 구조를 실제로 바꿨나?" → 아직 바꾸진 않았고, 개선안만 정리해 뒀다. 우선순위상 실제 반영은 못했다
- "이 한계가 실제 문제가 된 적 있나?" → 새로운 유형의 출석 조건 요청이 오면 서버 개발자가 다시 붙어야 해서, 원래 노렸던 만큼의 속도 개선은 못 봤다
- "왜 처음부터 JSON으로 안 했나?" → 당시엔 테이블 기반이 익숙했고 요구사항 범위 안에서는 충분하다고 판단했다. 이후 다른 사례를 보고 한계를 깨달았다

"AI 도구를 실무에 써본 적 있어요? 어디서 도움이 됐고, 어디서 한계를 느꼈어요?"

[예시 답안 - 약 45초]

네, 실무에서 AI를 역할별 서브 에이전트로 나눠서 쓰고 있습니다. 저희 팀은 9명이 17개 서비스를 나눠 맡다 보니, 처음 보는 프로젝트를 빠르게 파악해야 할 일이 잦았습니다. 기획 문서를 요구사항으로 정리하는 것, 레거시 코드를 분석하는 것, 작업을 최소 단위로 쪼개 로드맵을 짜는 것을 각각 다른 에이전트로 나눠 맡겼습니다.

가장 도움이 된 건 낯선 코드를 파악하는 초기 속도입니다. 파악이 빨라진 만큼, 구조를 깊게 들여다볼 시간이 늘었습니다.

한계는 AI가 정리한 내용이 실제 코드 동작과 다를 때가 있다는 겁니다. 그래서 결과를 그대로 쓰지 않고 항상 코드와 대조해 확인하고, 최종 판단은 직접 합니다.

[주요 키워드]

- 활용: 역할별 서브 에이전트 분리 (요구사항 정리 / 레거시 분석 / 로드맵 작성) — 9명이 17개 서비스 담당하는 환경에서 낯선 프로젝트 빠른 파악 위해
- 도움된 점: 낯선 코드 파악 초기 속도 향상 → 구조를 깊게 볼 시간 확보
- 한계: AI 정리 내용이 실제 코드 동작과 다를 때 있음 → 결과를 그대로 안 쓰고 코드와 대조 검증, 최종 판단은 직접

[암기용 3비트]

1. 활용 — 역할별 서브에이전트(요구사항/레거시분석/로드맵), 낯선 프로젝트 빠른 파악 위해
2. 도움 — 초기 파악 속도 향상 → 깊게 볼 시간 확보
3. 한계 — AI 결과가 실제 코드와 다를 수 있음 → 항상 대조 검증, 최종 판단은 직접

[예상 후속 질문 대비]

- "AI 결과가 틀렸던 구체적 사례는?" → [준비 필요 — 실제 사례 하나 정리해두면 좋음]
- "AI 없이 일하던 때와 비교하면?" → 프로젝트 착수 전 파악 단계가 눈에 띄게 짧아졌다. 다만 최종 코드 작성이나 판단은 이전과 동일하게 직접 한다
- "AI를 신뢰 못하면 왜 쓰나?" → 처음부터 안 믿는 게 아니라, 반복적이고 시간 걸리는 정리·분석은 맡기고 검증은 사람이 하는 분업이라고 생각한다
- "팀 다른 사람도 이 방식을 쓰나?" → [준비 필요 — 실제 여부]

"버그를 직접 추적해 해결한 경험을 구체적으로요."

[예시 답안 - 약 50초]

마이크로볼츠에서 운영툴 로그가 하루 12만 건씩 비어 보이던 문제가 가장 기억에 남습니다.

처음엔 로그가 아예 안 쌓이는 줄 알았는데, 데이터는 오류 보관 테이블에 남아 있었습니다. 원인 구간을 좁히려고, 로그 적재에 관여하는 프로시저의 처리 단계마다 상태 값을 따로 기록하게 했습니다. 그 결과 MySQL 이벤트로 주기 실행되는 파티셔닝 프로시저에서, Bulk Insert가 한 번 실패하면 그 배치 전체가 파티션 테이블로 안 넘어가는 구조를 찾았습니다.

해결은 두 방식을 놓고 고민했습니다. 성능을 지키되 일부 누락을 감수하는 방식과, 실패 건을 하나씩 다시 넣어 누락을 없애는 방식이요. 로그는 운영의 근거라 정합성을 택했고, 실패 시 단건 재삽입으로 바꿨습니다. 이후 1년간 재발이 없습니다.

[주요 키워드]

- 증상: 운영툴 로그가 일 12만 건 누락처럼 보임
- 1단계 확인: 데이터는 오류 보관 테이블에 존재 (완전 유실 아님)
- 추적 방법: 프로시저 처리 단계마다 상태 값을 기록 → 원인 구간을 단계별로 좁혀감
- 원인: 파티셔닝 프로시저에서 Bulk Insert 1회 실패 시 배치 전체가 파티션 테이블로 미이관
- 해결: 정합성 우선 → 실패 시 단건 재삽입 / 이후 1년 재발 없음

[암기용 3비트]

1. 증상·확인 — 로그 12만 건 누락처럼 보임 /
2. 추적 — 프로시저 단계별 상태 값 기록 → Bulk Insert 실패 시 배치 전체 미이관 발견
3. 해결 — 정합성 우선, 실패 건 단건 재삽입 / 1년 재발 없음

[예상 후속 질문 대비]

- "재현이 안 되는 문제는 어떻게 추적하나?" → 처리 흐름을 단계로 쪼개고, 각 단계에 흔적(상태 값)을 남겨 어디서 멈추는지부터 확인한다
- "왜 그 방식으로 원인 구간을 좁혔나?" → 로그 전체를 한 번에 보는 대신, 처리 파이프라인의 각 단계가 정상 통과했는지를 따로 확인하면 실패 지점이 좁혀진다
- "성능 저하는 감수했나?" → 실패가 몰릴 때만 느려진다. 유실된 로그는 되돌릴 수 없다고 판단해 정합성을 우선했다
