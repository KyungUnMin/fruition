1. 고객이 무리한 요구를 하며 화를 내고 있습니다. 어떻게 상황을 해결하시겠습니까?

[예시 답안 - 약 30초]
 먼저 요구를 반박하기보다, 왜 화가 났는지를 끝까지 듣겠습니다. 무리한 요구 뒤에는 대개 급한 일이 막혀 있습니다.
 그다음 요구가 아니라 목적을 확인합니다. 무엇을 하려는지 물으면, 원래 요구보다 나은 방법이 보이는 경우가 많습니다.
 마지막으로 지금 가능한 선을 제시합니다. 되는 것과 안 되는 것, 언제까지 가능한지를 구체적으로 전달해 막연한 거절로 끝나지 않게 하겠습니다.

[주요 키워드]
 - 경청: 요구 반박보다 "왜 화났는지" 먼저 - 뒤에는 막힌 급한 일
 - 목적 확인: 요구가 아니라 목적을 물음 -> 더 나은 방법
 - 차선 제시: 되는 것/안 되는 것/언제까지를 구체적으로

[암기용 3비트]
 1. 경청 - 왜 화났는지 끝까지
 2. 목적 확인 - 요구 말고 목적
 3. 차선 제시 - 되는 것·안 되는 것·기한 구체적으로

[예상 후속 질문 대비]
 - "그래도 안 통하면?" -> 그 자리서 결론내지 않고 회신 시점을 명확히 잡아 대화를 끊는다
 - "차선도 없는 요구라면?" -> 왜 안 되는지와 대안을 함께. 거절만 남기지 않는다


2. 팀원과 의견이 다를 때 직접 대화로 해결하는 것과 팀장이나 제3자를 통해 조율하는 것 중에서 더 효과적이라고 생각하는 것과 이유를 말씀해주세요.

[예시 답안 - 약 35초]
 직접 대화가 더 효과적이라고 생각합니다. 의견 차이는 대부분 서로가 가진 정보나 전제가 달라서 생기고, 이건 당사자끼리 근거를 맞대야 가장 빨리 좁혀집니다. 3자를 거치면 전달 과정에서 맥락이 빠지고 시간도 더 걸립니다.
 다만 감정이 상해 대화가 겉돌거나 같은 논쟁이 반복될 때는 팀장에게 판단 기준을 요청하는 게 낫습니다. 결정을 넘기는 게 아니라, 우선순위 기준을 받아 다시 논의하기 위해서입니다.

[주요 키워드]
 - 선택: 직접 대화 우선
 - 이유: 의견 차이 = 정보·전제 차이 -> 당사자끼리 근거 맞대야 빨리 좁혀짐 / 3자 거치면 맥락 손실·시간 소요
 - 예외: 감정 상함 / 논쟁 반복 -> 팀장에게 "판단 기준" 요청 (결정 위임 아님)

[암기용 2비트]
 1. 직접 대화 우선 - 의견 차이는 정보·전제 차이라 당사자끼리가 제일 빠름
 2. 예외 - 감정 상하거나 반복될 때만 팀장에게 우선순위 기준을 받아 다시 논의

[예상 후속 질문 대비]
 - "직접 대화가 안 통한 경험은?" -> 근거를 문서로 정리해 공유하면 감정이 빠지고 사안만 남는다
 - "3자가 개입하면 안 좋은가?" -> 나쁘다는 게 아니라 순서의 문제. 당사자 시도가 먼저


3. 동료가 실수를 했을 때, 아무 일 없었다는 듯이 넘어가는 것과 다소 분위기가 어색해질지라도 실수를 언급하는 것 중에서 더 필요하다고 생각하는 것과 이유를 말씀해주세요.

[예시 답안 - 약 35초]
 어색해도 언급하는 게 필요하다고 생각합니다. 서버 쪽 실수는 넘어가면 사라지는 게 아니라 코드나 데이터에 남아, 나중에 장애로 더 크게 돌아옵니다.
 대신 방식이 중요합니다. 사람이 아니라 사안을 짚고, 공개적으로 몰아세우지 않고, "이 부분 이렇게 되어 있던데 확인해봤냐"는 식으로 사실 확인처럼 전달합니다. 저도 지적받는 입장이 될 수 있으니, 서로 편하게 말할 수 있는 분위기를 만드는 게 결국 팀에 이득입니다.

[주요 키워드]
 - 선택: 어색해도 언급
 - 이유: 서버 실수는 코드·데이터에 남아 나중에 장애로 확대
 - 방식: 사람 아닌 사안 / 공개 비난 X / 사실 확인처럼 ("이렇게 돼 있던데 확인해봤냐")
 - 전제: 나도 지적받을 수 있음 -> 서로 편히 말하는 분위기가 팀에 이득

[암기용 3비트]
 1. 언급한다 - 서버 실수는 안 사라지고 장애로 커진다
 2. 방식 - 사람 말고 사안, 공개 비난 없이, 사실 확인처럼
 3. 전제 - 나도 지적받을 수 있으니 편히 말하는 분위기가 이득

[예상 후속 질문 대비]
 - "언급했다가 관계가 나빠지면?" -> 비난이 아니라 확인으로 전달하면 대부분 문제되지 않는다. 반복되는 실수만 별도로
 - "사소한 실수도 다 짚나?" -> 서비스·코드에 영향이 남는지로 기준을 잡는다


4. 예산이 절반으로 줄어든 상황에서 프로젝트를 완료해야 합니다. 어떤 전략을 사용하시겠습니까?

[예시 답안 - 약 35초]
 먼저 목표를 다시 확인하고, 기능을 반드시 필요한 것과 있으면 좋은 것으로 나누겠습니다. 예산이 준 만큼 범위를 줄이는 게 먼저지, 같은 범위를 무리해서 끌고 가면 품질이 무너집니다.
 그다음 새로 만들 부분을 줄입니다. 기존 구조나 검증된 모듈을 재사용하고, 직접 개발할 곳과 가져다 쓸 곳을 나눕니다. 이해관계자에게는 이번 범위에서 무엇을 뺐는지 먼저 합의하고 진행하겠습니다.

[주요 키워드]
 - 1순위: 목표 재확인 -> 기능을 필수 / 부가로 분리, 범위부터 축소
 - 이유: 같은 범위를 무리하게 끌면 품질이 무너짐
 - 2순위: 신규 개발 축소 -> 기존 구조·검증된 모듈 재사용, 직접 개발 vs 가져다 쓸 곳 구분
 - 필수: 뺀 범위를 이해관계자와 먼저 합의

[암기용 3비트]
 1. 범위 축소 - 필수/부가로 나눠 필수만
 2. 신규 최소화 - 기존 자산·모듈 재사용
 3. 합의 - 뺀 것을 먼저 공유하고 진행

[예상 후속 질문 대비]
 - "그래도 필수 범위가 예산을 넘으면?" -> 일정을 나눠 단계 출시하거나, 기한·범위·인력 중 무엇을 조정할지 결정권자에게 선택지를 제시
 - "품질을 낮추는 건?" -> 눈에 안 보이는 안정성은 유지하고, 부가 기능 범위로 조절


5. 업무를 배울 때 동료나 선배가 귀찮게 여길지라도 모르는 것은 바로바로 질문하는 것과 일단 시간이 걸려도 최대한 알아본 이후에 질문하는 것 중에서 더 좋은 자세라고 생각하는 것과 이유를 말씀해주세요.

[예시 답안 - 약 35초]
 먼저 스스로 알아본 뒤 질문하는 자세가 낫다고 생각합니다. 다만 무한정이 아니라, 30분이면 30분처럼 시간을 정해두고 그 안에 안 풀리면 바로 묻습니다.
 스스로 찾아본 만큼 질문이 구체적이어져서 답하는 사람도 시간을 덜 씁니다. "이거 왜 안 되냐"가 아니라 "여기까지 확인했는데 이 부분이 막힌다"로 물으면 대화가 짧게 끝납니다. 반대로 서비스 장애처럼 급한 상황이면 알아보는 단계를 건너뛰고 바로 공유합니다.

[주요 키워드]
 - 선택: 먼저 알아본 뒤 질문 - 단, 시간 제한을 둠(예: 30분)
 - 이유: 스스로 찾은 만큼 질문이 구체적 -> 답하는 사람 시간 절약 ("여기까지 확인, 이 부분이 막힌다")
 - 예외: 장애 등 급한 상황이면 바로 공유

[암기용 3비트]
 1. 먼저 알아본다 - 단 시간 박스(30분)
 2. 이유 - 구체적 질문이 상대 시간을 아낀다
 3. 예외 - 급한 장애는 바로 공유

[예상 후속 질문 대비]
 - "시간 제한을 어떻게 정하나?" -> 일의 급함과 난이도로. 급하면 짧게, 여유 있으면 길게
 - "질문을 안 하고 헤매는 후배가 있다면?" -> 막히면 언제든 물어도 된다고 먼저 말해주고, 질문의 문턱을 낮춘다


6. 나의 능력을 인정받을 수는 있지만 성장에 도움이 되지 않는 프로젝트와 성장에는 큰 도움이 되지만 나의 존재가 크게 드러나지 않는 프로젝트 중에서 더 원하는 것과 이유를 말씀해주세요.

[예시 답안 - 약 32초]
 성장에 도움이 되는 쪽을 택하겠습니다. 아직 2년 차라, 지금은 눈에 띄는 것보다 할 수 있는 일의 범위를 넓히는 게 더 중요합니다.
 당장 티가 안 나도 실력이 쌓이면 이후에 맡을 수 있는 일이 달라지고, 결국 그게 더 크게 인정받는 길이라고 봅니다. 다만 존재가 안 드러나는 것과 팀에 기여를 안 하는 건 다르므로, 맡은 몫은 확실히 하겠습니다.

[주요 키워드]
 - 선택: 성장 쪽
 - 이유: 2년 차엔 가시성보다 할 수 있는 일의 범위 확장이 우선 / 실력이 쌓이면 인정은 따라옴
 - 단서: "존재가 안 드러남" != "기여 안 함" -> 맡은 몫은 확실히

[암기용 2비트]
 1. 성장 쪽 - 2년 차엔 실력 범위 확장이 먼저, 인정은 뒤따름
 2. 단서 - 안 드러나도 맡은 몫은 확실히 한다

[예상 후속 질문 대비]
 - "계속 안 드러나면 손해 아닌가?" -> 단기엔 그럴 수 있어도, 커리어는 길게 보면 실력이 곧 협상력
 - "인정받는 프로젝트는 전혀 매력 없나?" -> 매력은 있지만, 지금 단계에서 우선순위는 성장


7. 상사가 부당하다고 생각되는 업무지시를 했습니다. 어떻게 행동하시겠습니까?

[예시 답안 - 약 35초]
 먼저 부당하다고 느낀 이유가 판단 차이인지, 규정이나 윤리에 어긋나는 문제인지 구분하겠습니다.
 판단 차이라면, 지시의 의도를 먼저 확인하고 제가 우려하는 부분을 근거와 함께 한 번 더 말씀드립니다. 그래도 같은 지시라면 제가 못 본 맥락이 있을 수 있으니 따르되, 예상되는 리스크는 기록해 공유합니다.
 다만 규정이나 윤리에 어긋나는 일이라면 그건 따르지 않고, 정식 경로로 문제를 제기하겠습니다.

[주요 키워드]
 - 1단계: 구분 - 판단 차이 vs 규정·윤리 위반
 - 판단 차이: 의도 확인 -> 근거 들어 재의견 -> 그래도면 따르되 리스크 기록·공유
 - 규정·윤리 위반: 따르지 않음 -> 정식 경로로 제기

[암기용 3비트]
 1. 구분 - 판단 차이냐, 규정·윤리 위반이냐
 2. 판단 차이 - 의도 확인, 근거로 재의견, 그래도면 따르되 리스크 기록
 3. 위반 - 따르지 않고 정식 경로

[예상 후속 질문 대비]
 - "리스크를 기록해 공유한다는 게 상사를 못 믿는 것처럼 보이지 않나?" -> 책임 회피가 아니라, 나중에 문제가 생겼을 때 빨리 대응하기 위한 것
 - "부당한지 애매하면?" -> 혼자 판단하지 않고 동료나 선배 의견을 먼저 들어본다


8. 정해진 마감일을 지키지 못 하더라도 완벽하게 일을 하는 것과 정해진 마감일은 지킬 수 있지만 미완성으로 일을 하는 것 중에서 더 중요하다고 생각하는 것과 이유를 말씀해주세요.

[예시 답안 - 약 35초]
 마감을 지키는 쪽이 더 중요하다고 생각합니다. 게임 서버 일은 마감이 대개 런칭이나 이벤트 같은 외부 약속이라, 늦으면 저 혼자가 아니라 전체 일정이 밀립니다.
 대신 "미완성"을 범위를 줄인 완성으로 바꿉니다. 반드시 돌아가야 하는 핵심은 완성해서 내보내고, 부가 기능은 다음으로 미룹니다. 무엇을 뺐는지는 미리 공유합니다. 완벽은 대개 계속 미뤄지기 때문에, 기한 안에서 최선을 정하는 게 현실적입니다.

[주요 키워드]
 - 선택: 마감 우선
 - 이유: 서버 마감은 런칭·이벤트 등 외부 약속 -> 늦으면 전체 일정이 밀림
 - 방식: "미완성" -> "범위를 줄인 완성" (핵심은 완성, 부가는 다음, 뺀 것 미리 공유)
 - 관점: 완벽은 계속 미뤄짐 -> 기한 안 최선을 정함

[암기용 3비트]
 1. 마감 우선 - 서버 마감은 외부 약속, 늦으면 전체가 밀림
 2. 미완성 대신 범위를 줄인 완성 - 핵심 완성, 부가 연기, 뺀 것 공유
 3. 완벽은 계속 미뤄진다 - 기한 안에서 최선

[예상 후속 질문 대비]
 - "안정성도 부가로 미룰 건가?" -> 아니다. 유저 데이터·결제처럼 되돌릴 수 없는 부분은 핵심에 넣는다
 - "마감이 비현실적이면?" -> 미리 알리고 범위·기한·인력 중 조정안을 제시


9. 야근이 계속되어 개인시간이 없어진 상황입니다. 어떻게 해결하시겠습니까?

[예시 답안 - 약 35초]
 먼저 이게 일시적인 피크인지, 구조적으로 계속될 상황인지 봅니다. 런칭 직전처럼 일시적이면 감수하고, 끝난 뒤 쉬는 걸로 조정합니다.
 계속될 상황이면, 제 업무 목록과 걸리는 시간을 정리해 팀장과 우선순위를 다시 잡습니다. 지금 안 해도 되는 일을 빼거나, 반복 작업을 자동화하거나, 일을 나누는 방향입니다. 혼자 참고 버티면 결국 실수가 늘어서, 문제를 드러내는 게 맞다고 봅니다.

[주요 키워드]
 - 1단계: 구분 - 일시적 피크 vs 구조적 과부하
 - 일시적: 감수, 끝난 뒤 회복
 - 구조적: 업무 목록·소요 시간 정리 -> 팀장과 우선순위 재조정 (불필요한 일 제거 / 자동화 / 분담)
 - 근거: 혼자 버티면 실수가 늘어난다 -> 드러내는 게 맞음

[암기용 3비트]
 1. 구분 - 일시적이냐 구조적이냐
 2. 일시적이면 감수 후 회복
 3. 구조적이면 업무 정리해 팀장과 우선순위 재조정 (제거·자동화·분담)

[예상 후속 질문 대비]
 - "팀 전체가 야근이면?" -> 개인이 아니라 팀 차원의 일정·인력 문제로 보고, 회고 자리에서 데이터로 제기
 - "그냥 참는 사람으로 보이고 싶지 않나?" -> 참는 것과 책임감은 다르다. 지속 가능해야 오래 기여한다


10. 즉흥적인 친구, 계획적인 친구와 함께 여행 갔을 때 어떻게 할 것인가요?

[예시 답안 - 약 30초]
 둘 다 장점이 있어서 역할을 나누겠습니다. 이동이나 숙소, 꼭 가야 하는 곳처럼 틀어지면 곤란한 건 계획적인 친구 쪽에 맞추고, 그 사이 남는 시간은 즉흥적인 친구가 하자는 대로 둡니다.
 의견이 부딪히면 "이 여행에서 뭘 제일 하고 싶었는지"를 기준으로 정합니다. 저는 중간에서 양쪽 의견을 정리하고 결정을 돕는 역할을 하겠습니다.

[주요 키워드]
 - 역할 분담: 틀어지면 곤란한 것(이동·숙소·필수 코스) = 계획대로 / 남는 시간 = 즉흥에 맡김
 - 갈등 시 기준: "이 여행에서 제일 하고 싶었던 것"
 - 내 역할: 중간에서 의견 정리하고 결정을 도움

[암기용 2비트]
 1. 역할 분담 - 틀어지면 곤란한 건 계획대로, 여백은 즉흥대로
 2. 갈등 나면 "여행의 목적"을 기준으로, 나는 조율 역할

[예상 후속 질문 대비]
 - "본인은 어느 쪽에 가깝나?" -> 계획형에 가깝다. 다만 여행처럼 변수 많은 일은 여백을 남겨두는 편
 - "둘이 계속 싸우면?" -> 억지로 합치지 않고, 반나절씩 각자 방식대로 다니고 저녁에 합류하는 식으로 나눈다
